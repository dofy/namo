# 首次反馈与执行过程卡片计划

调研日期：2026-10-27。状态：**P0 / P1 已实现并通过隔离验证；P2 图片预览、P3 流式更新尚未实现。未改在线配置、未发送测试消息或升级服务**。现有行为与已验收事实见[飞书日常回复](chat-experience.md)。

本轮默认首卡合并窗口为 200 毫秒，仍保留已有显式延迟。公开进展按 run 保存有界快照与 revision；完整 commentary、计划计数、工具开始 / 结束摘要和已校验文件路径驱动同卡片更新。表情与卡片更新分为独立单写者；最终结果不等待低优先级更新。出站发送开始与平台回执时间已保存。以下延迟证据是修改前的调研样本，不代表本轮上线表现；P95 与真实客户端收件仍待部署后验收。

本轮验证：`pnpm test` 364/364 通过（含服务端与 UI 构建）；`pnpm run smoke:codex` 官方 app-server 初始化、登录状态和权限握手通过，未运行真实模型推理。回归包括慢表情 / 慢更新、队列、wait / resume 同意图、重启、旧事件 / 重复事件 / 提前通知、脱敏与终态竞争。

## 结论与实施顺序

可以让同一张执行卡片展示公开的进展摘要、当前动作、工具完成情况和受控图片预览。首轮应先移除首卡的长等待，再增加真实事件驱动的进展，最后补图片预览；不必先迁移整个飞书卡片协议。

默认展示用户可读的“正在做什么 / 已完成什么 / 接下来做什么”。不展示模型原始思维链、`reasoning.content`、`item/reasoning/textDelta`、完整命令参数、工具输入输出、补丁正文或内部日志。公开进展摘要和内部推理是不同数据契约。

## 修改前的实现与延迟证据

- `src/config.ts`：`progressDelayMs` 默认 12000，阶段更新最短间隔 5000，无新阶段的状态确认间隔 30000；现有配置校验也限制了可设置的最小值。
- `src/engine.ts` / `src/tasks.ts`：接受并创建任务后，进度消息先进入 `deferred`，到期才可发送；任务提前完成则抑制未发送的提示。快速受理主要由表情承担。
- `src/feedback.ts`：`run_activity` 每个 run 只保留最后一个粗粒度 phase；同阶段按 30 秒心跳处理，命令换成另一个命令也无法保留详细进展。
- `src/runtime.ts`：主轮次主要消费 `item/started`、`item/completed`、`turn/completed`，将命令 / 文件 / 工具事件映射为阶段；未将公开 commentary、计划或摘要增量接入卡片。任何 agentMessage 都可能让阶段变成 answering，不能据此认定正在生成最终答案。
- `src/evidence.ts` 已有安全的命令类别、相对文件路径、退出结果和图片产物路径投影；可复用，但不是完整日志，也没有读取文件数量等通用统计。
- `Feedback.tick` 先等待表情操作再处理更新，`Feedback.finalize` 也可能等待在途操作；网络较慢时存在额外等待可能。`Engine.flush` 当前还有统一发送节奏和顺序约束。需要补时间点确认实际占比，不能将这些可能性当成已经量化的根因。

只读抽查当前数据库中最近 5 个已发送进度卡片的私聊任务，并用官方 SDK 读取对应平台消息创建时间：

| 指标 | 观察结果 |
| --- | --- |
| 本机接收至 task 启动 | 4–12 毫秒 |
| 本机接收至飞书创建首卡 | 12.665–13.030 秒 |
| 当前首卡延迟配置 | 12 秒 |

样本只包含“确实发送了进度卡片”的任务，不含快速完成后被抑制的任务；不能据此推断全量 P95。表中“本机接收”以 `inbox.createdAt` 入站登记时间近似，精确提交时间仍待补充。平台创建时间也不等于用户客户端显示 / 已读时间。本计划只保留时延汇总，不写入样本正文、用户 / 聊天标识、凭据、卡片操作 token 或截图。

结论：这些样本中主要的可消除等待来自 Namo 主动延迟首卡，而不是任务排队。尚未测出 Codex 初始化、首 token 与客户端渲染各自的时延。

## 用户看到的过程

第一张卡在持久接受后尽快显示“已收到”，再按真实状态变成“排队中 / 正在连接 / 正在执行 / 等待补充 / 已结束”。排队不冒充执行；受理不冒充模型已经开始。

执行时建议保留四块简短信息：

```text
正在执行 · 已用 38 秒

当前：运行相关测试
进展：已定位问题，并修改了 2 个文件

最近活动
✓ 查看项目约定
✓ 应用文件补丁
• pnpm test 运行中

接下来：检查结果并整理答复
[有合规产物时显示一张预览图]

[查看详情] [停止任务]
```

示例内容不是预置话术：没有对应事件时不生成这些完成项、数量或“接下来”。计划意图、工具执行事实与验收结论分别标记。命令正常退出只说明命令结果，不写成“功能验收通过”。

过程区保留最近 3–5 条有意义活动，正文摘要控制在约 100–200 字；其他记录放详情。无新事件时只标记“仍在运行，暂无新的公开进展”和最近活动时间，计时 / 心跳不能充当进展。前台卡片不显示自动记忆提取等其他后台任务的活动。

## P0：首卡快速出现

1. 增加独立的“受理卡片”策略，默认在入站、任务与出站意图持久提交后异步发送。可留约 200 毫秒的合并窗口：最终答复已就绪就直接交付；否则不再等待 12 秒或模型首个输出。该窗口是拟议产品值，不是修改现有配置后的实测值。
2. 受理、排队、运行和终态更新复用同一张 live card，固定原消息 / 话题与任务关联；修订、wait / resume 不额外制造无关首卡。原来的慢任务延迟策略可作为可选模式保留。
3. 表情和首卡分开调度；表情失败 / 超时不挡首卡，首卡失败不挡模型。结果交付也不应等待低优先级心跳或旧卡片更新完成。给首卡和最终答复优先级，同时保留同聊天顺序、终态栅栏和单写者。
4. 表情可保留为更早的反馈，但不再承担唯一的可见确认。未授权、未触发及未持久接受的消息继续不回应。

验收目标（正常网络）：本机接收至飞书接受首个可读反馈 P95 ≤ 2 秒；即使 Codex 冷启动、长期排队或材料解析较慢，也能先给真实受理状态。这是开发目标，不承诺平台 / 客户端延迟。快速任务不出现滞后的“正在执行”卡片。

## P1：公开摘要与工具进展

新增有界、可恢复的 `PublicProgressEvent` 投影，按 task / run / thread / turn / item / sequence 绑定，至少区分：受理状态、计划、公开说明、工具活动、文件变更、产物、心跳和终态。通用卡片只依赖这套投影，不直接依赖 Codex 的 wire method，方便 R7 的其他执行器按能力接入。

| 信息 | Codex 来源与处理建议 |
| --- | --- |
| 公开进展说明 | 优先 `agentMessage.phase=commentary`；增量拼接到完整句再采用，过滤秘密、路径和不适合当前会话的内容。补充运行指令，要求开工和关键阶段给简短公开说明，但不额外调用模型给每个事件写摘要。 |
| 计划与步骤 | `turn/plan/updated` / plan item；作为“当前计划”展示，不假设每轮必有计划，不把模型标记完成等同外部验收。 |
| 思路摘要 | 只评估官方明确提供的用户可读摘要渠道；没有时展示公开说明与动作事实。不得把原始 reasoning 换个标题直接发出，也不补造摘要。 |
| 工具调用 | item started / completed；显示白名单工具类别、允许的简短动作名、运行 / 已结束 / 失败状态。禁止透传参数、URL 查询、shell 命令全文或完整输出。 |
| 文件变更 | 复用已校验的相对路径和补丁数量；明确是“已应用补丁”，不能据此声称构建 / 功能验证成功。 |
| 网页 / MCP / 图片活动 | 只保留公开类别与安全名称，如“查询文档”“查看任务图片”；不自动公开搜索词、请求参数或本机完整路径。 |

持久化最近的公开快照和必要状态事件，不保存原始推理或 token 全流。先缓冲再核对 turn 身份，处理“完成通知先于请求响应”、旧 item、重复事件和多工具并行；重启可恢复展示，但不重跑模型。

更新比较应使用 `contentRevision / contentHash`，不能只比较 phase。先沿用约 5 秒的普通更新节奏，合并同一窗口的变化；重要等待 / 终态优先。真实内容更新和 30 秒无进展心跳分别调度，防止连续同类工具都被误判为“无变化”。具体节奏再按真实客户端和平台频控调整。

验收：单个长命令、多个连续命令、文件修改、公开 commentary 与计划均有可核对的不同进展；无事件时不虚构步骤 / 百分比 / ETA；点击详情不停止原卡片更新；多用户、多群话题和并行工具不串线。终态不能被晚到的进度覆盖。

## P2：受控图片预览

只预览当前任务明确产出的图片或经授权的任务截图，不扫描目录、不自动回显所有输入附件、不抓取模型输出的任意外部图片 URL。图片必须经过项目边界、禁止路径、符号链接、签名、尺寸与大小检查；不能只相信扩展名或 `imageView` 路径。

复用现有产物校验，补充预览图片上传与卡片 `img_key` 组件。按 task + 文件内容哈希缓存上传结果，限制为 1–2 张缩略图，并区分“生成中”“预览已就绪”和最终交付。未完成写入的图片不得上传；生成过程内部图片 / 桌面截图可能有隐私，不能默认公开。

上传和刷新走独立低优先级任务，不挡首卡、正文或最终结果；失败则显示“预览暂不可用”，不重跑模型或无止境重复上传。上传成功但卡片更新未知时先核对状态，不将超时视为未生效。最终图片交付与卡片预览分别保留状态。

## P3：可选的 CardKit 流式体验

如果 P0 / P1 的效果仍不足，再单独评估飞书 CardKit / JSON 2.0：SDK 已提供卡片实体、流式文本、`streaming_mode` 与递增 `sequence` 的契约，适合持续文字更新。现有 `im.message.patch` 足以先实现阶段摘要与工具进展。

迁移前核实应用权限、当前 API 的应用级 / 单卡片频控、payload 上限、卡片实体有效期、共享更新和桌面 / 移动端兼容性；不要把不同 API 的配额混用。不迁移审批、等待按钮和最终结果等全部卡片作为首轮前置条件。若启用流式，仍只输出公开内容，必须有全局和单卡限流、递增版本及终态优先级。

## 时延观测与验证

补充接收、入站提交、受理出站入队、发送开始 / 平台回执、runner 启动、Codex 初始化完成、首个公开事件、首次过程更新、最终结果就绪与发送回执等时间点。当前 `message_feedback.updatedAt` 会被后续表情移除覆盖，`run_activity.updatedAt` 也只表示最后活动，不能拿它们倒推首次反馈延迟。

分别统计首个可读反馈、排队、执行器连接、首公开事件和最终交付耗时；记录超时 / 限流 / 未知结果，不能从样本中排除失败后再宣称达标。后续若 Codex 初始化占比显著，再评估进程预热 / 连接复用，不能以破坏独立 runner、权限快照或取消边界为代价。

验证顺序：安全事件投影与状态机 → fake runner / 可控慢 SDK 的重启及竞争测试 → 隔离卡片预览 → 官方 Codex 实测 → 经明确授权的飞书私聊和群话题收件验收。需覆盖慢表情、慢卡片更新、材料解析、冷启动、排队、快任务、取消、超时、失联、长时间任务按钮过期、未知发送、终态竞争和服务重启。测试数量、平台接受和客户端实际显示分别报告。

## 调研来源与待复核项

- [Codex app-server 官方协议](https://learn.chatgpt.com/docs/app-server)：公开 agent message、计划、工具与图片 item，以及摘要 / 原始 reasoning 的不同事件；具体字段以安装版本生成的 schema 复核。可读摘要与计划并不保证每轮产生。
- [飞书消息 API 概述](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/reference/im-v1)：当前应用发送的卡片可以通过消息接口更新；本项目 `FeishuTransport.updateCard` 已使用官方 SDK 的 `im.message.patch`。
- [飞书消息内容结构](https://open.feishu.cn/document/server-docs/im-v1/message-content-description/create_json)：图片引用使用上传后取得的图片 key。
- [CardKit 流式更新](https://open.feishu.cn/document/cardkit-v1/streaming-updates-openapi-overview) / [流式文本接口](https://open.feishu.cn/document/cardkit-v1/card-element/content)：新协议路线。安装的官方 Node SDK `1.76.0` 类型注释已核对相关接口及流式前提；部分官方页面正文抓取受限，本次不引用未经独立确认的数值配额或权限清单，实施前重新核实。

本计划只改变反馈和展示，不扩大工具权限，也不开放后台派工、自动发布或对外发送权限。R7 适配器和自动记忆是独立工作，不能因本计划改写其状态或当作已经上线。
