# 独立运行进程（M3 第一批）

独立运行机制自 schema 5 引入，当前源码继续使用该机制。历史运行与重启验证见[发布历史](archive/release-history.md)；本页维护生命周期与恢复契约。

## 生命周期

接收服务负责身份校验、持久化入站、调度与出站投递。每次任务运行在启动模型前保存唯一运行编号、持有者和冻结输入，再启动独立 Node 进程。执行进程通过事务将 `starting` 变为 `running`，登记自身 PID，只有成功取得这次运行的进程可以启动官方 Codex。重复或迟到的启动不会再执行一次。

执行进程沿用指定的官方登录、模型提供方、目录和权限；启动时核对配置指纹与任务权限指纹。任务途中接收服务退出或重启，原执行进程继续工作。新接收服务根据原运行记录重新关联，保留同聊天、重叠项目目录互斥和全局并发名额。不会将运行中的修订重新拼入初始输入。

执行证据即时持久化；运行结束后，证据终态与执行结果一起落库。接收服务再将任务终态及出站内容事务化保存，之后按既有发送流程取得回执。接收服务不在线时结果留在数据库，恢复后发送，不为投递重跑模型。独立执行进程没有飞书接收或发送能力。

`runner_events` 记录领取、执行器启动、thread / turn 绑定、修订提交与回执、完成、失联及人工核对等事件。事件只含类型和时间；prompt 与结果保存在受保护的任务库，不进入事件流水、状态 API 或日志。任务详情可查看运行状态、PID、最后记录时间及事件；这些信息不等于当前进程活性证明。

## 停止与失联

- Ctrl+C、`service stop / restart / uninstall` 停止的是接收服务；已开工的任务继续。需要停止任务时，使用 `/cancel`、任务卡片或本地工作台先保存取消请求。接收服务离线时，本地工作台仍可保存取消请求，执行进程自行读取。
- 用户取消会停止所属 Codex 进程组，保留已发生的操作与部分证据。取消不能撤销文件或外部效果。
- 取消与运行完成按数据库事务提交顺序判定：取消先提交，运行最终记为取消；完成先提交，飞书命令、卡片及本地工作台都拒绝再确认停止，提示查看已保存的结果。收到停止请求不代表此前操作已撤销。
- 心跳过期不会转移运行归属。明确发现执行进程退出，或启动登记超过期限时，记录失联并隔离该次运行；不重新启动模型。迟到进程不能领取已经隔离的运行。
- 失联可能留下执行器或其他后代进程，因此项目与并发占位继续保留。通过本机异常核对入口确认进程、子进程和外部效果已检查后，才能标记已核对并解除占位；飞书端不能解除。原执行或 Codex PID 仍存在 / 状态不明时拒绝解除；在 POSIX 系统还检查 Codex 所属进程组，即使组长已退出，只要后代仍在原组内，就继续保留占位。检查使用信号 0，不终止进程，也不向可能已复用的 PID 发出终止信号。解除占位不重跑原任务。
- PID 和心跳只用于保守诊断；PID 复用可能造成继续阻塞，需要本机人工检查。自行脱离原进程组的后代、远程操作及外部效果仍须人工核对，进程组消失不是所有副作用已结束的证明。Windows 不提供此 POSIX 进程组检查，不能据此宣称已验证同等边界。

修订先保存 `submitting` 再交给原执行器，取得明确回执后保存 `accepted / rejected / not_active`；结果不明保存 `unknown`。接收服务重启不改变仍由原进程提交的修订；运行进程失联时未取得回执的修订转为未知，不自动重送。

## 维护和兼容性

schema 5 新增 `runner_jobs / runner_events`，不重写旧表。旧 schema 4 的读操作不会迁移，写操作与新运行必须先在维护窗口升级。旧任务没有独立运行记录，保留旧版中断处理，不假装可续接。

完整停机、备份、升级或卸载前，先完成 / 取消全部任务并处理失联占位，再停止接收服务；单独停止接收服务不再代表数据库和执行环境静止。运行期间做一致性数据库备份必须使用 SQLite backup，不能只复制主文件。工作台配置应用拒绝未结束或失联的运行；手工替换配置不能扩大已经开始的任务权限。

独立 runner 负责单机已有任务；人工和 GitHub 检查等待分别见[人工等待](waits.md)、[外部等待](external-waits.md)。不提供定时任务或持续派工；[Git push 审批](approvals.md)仅提供有限保护，不包含通用部署。

## 验证范围

隔离测试覆盖接收服务退出与重启、停机期间保存结果、重新关联与投递、修订、取消竞争、项目互斥、并发、重复启动、权限变化、失联及迁移保留。真实验证记录见[发布历史](archive/release-history.md)，待补场景见[后续计划](development-plan.md)。

2026-10-27 P0 组合验证补充了真实接收进程 SIGKILL、独立 SQLite 写入者的恢复 / 取消竞争、等待落库后的 worker 丢失，以及平台接受后回执落库失败。修复了组长退出但同组后代存活时可提前解除占位的问题。详细证据与待验范围见 [P0 恢复验证](archive/p0-recovery-verification-20261027.md)。
