# P0 恢复与取消组合验证（2026-10-27）

范围：Codex 主线上的等待中重启、取消与恢复竞争、失联 worker、未知投递。全部故障注入使用临时 SQLite、临时项目、协议替身和自建测试进程；没有调用真实模型或飞书收发，没有停启现有服务、修改其配置或业务数据。验证分支为 `seven/codex-core-flow`。

## 发现与修复

失联任务的本机“已核对”原来只检查 worker PID 与 Codex PID 是否消失。在 POSIX 系统，Codex 以独立进程组运行；组长退出后，组内子进程可能继续操作项目。原逻辑会允许解除项目 / 并发占位，新任务可能与残留进程重叠执行。

使用独立进程组复现：组长退出，真实子进程仍存活；原代码的“应拒绝核对”断言失败（`Missing expected exception`）。修复后，保留两个 PID 检查，并以信号 0 检查 Codex 进程组。组仍存在或状态不明时拒绝解除；不写核对审计、不改变 lost 状态、不终止任何进程。测试清理组内进程后，再次核对才允许解除。更新了中英文诊断提示，无 schema 或配置格式变化。

这项检查不覆盖主动脱离原进程组的后代、远程进程或外部效果；本机操作者仍需核对实际影响。Windows 沿用原 PID 检查，未据此标记与 POSIX 同等验证。

## 场景与证据

| 场景 | 故障或竞争条件 | 核对结果 |
| --- | --- | --- |
| 等待中接收服务硬退出 | 真正 SIGKILL 测试接收进程，已持久化 open wait，worker 已完成本轮 | 新接收端保留原问题及 thread；回答前无新推理；重复消息去重，回答后只增加一次续接 |
| 回答已保存但尚未运行 | 接收端停用时保存回答，数据库关闭 / 重开两次 | 原 task、thread、回答保留；仅传恢复输入，不重放原始操作；两轮运行、一次 wait_reply |
| 取消与回答同时发生 | 两个独立进程 / SQLite 连接同时提交 | 事务串行化；取消成功后任务终态为 cancelled，重启及迟到回答不能再次运行；原有测试另覆盖两种确定提交顺序 |
| 等待请求刚落库，worker 丢失 | `requested` 已落库及 ACK，但中断回执尚未完成；杀死测试 worker，再重启接收端 | 等待变 uncertain，不发送可回答问题；恢复与取消不能解除 lost 占位；重启后仍阻止复用，须本机核对 |
| runtime 组长退出、后代存活 | 真实独立进程组与存活子进程 | 修复前可提前解除，修复后拒绝；进程组结束后才允许本机核对；原任务不重跑 |
| 平台接受后回执保存失败 | 测试 sender 已返回成功，SQLite trigger 拒绝写入 `sent` | 出站保留 sending，接收端停止调度；重开后标为 unknown，无伪造平台回执、无自动重发或推理重跑 |
| 对未知投递显式重试 | 本人确认重复风险并提交带快照的核对请求 | 只重发已保存结果，使用新 UUID，审计请求幂等；模型调用总数保持一次；再次重启不重发 |

测试入口：`test/recovery-combinations.test.ts`、`test/runner-wait.test.ts`；同时复跑 `runner.test.ts`、`waits.test.ts`、`recovery.test.ts`，覆盖旧有取消完成竞争、失联占位、权限与原生上下文失配保护。

## 合并复核

2026-10-27 与 main 中的 Skills 权限修复合并验证。全量测试发现竞争夹具把恢复回答保存成了普通文本：取消先提交时，重启会把这条无引用消息当作独立任务，而非恢复原任务。将持久化输入改为真实的 `/resume` 命令，并补上回答先提交、取消先提交的确定顺序，保留独立 SQLite 写入者的并发测试与不重复执行断言。

修正后恢复专项 39 项、全量 `pnpm test` 477 项通过；此前官方 Codex 握手已通过，测试修正不改变运行代码。本批经合并复核交付 main，原有未合并验证记录保留为历史。没有调用模型、发送飞书消息、改写配置 / 认证 / 运行数据或切换当前后台服务；真实链路验收仍按下述范围单独进行。
