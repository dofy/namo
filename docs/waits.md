# 等待用户补充后继续（M3 第二批）

本批实现 schema 6 的人的回复等待与恢复。2026-10-26 已备份并升级现有实例，随后上线 schema 7 选项按钮；当前线上为 schema 7。CI / PR 事件适配、定时器和受控推送审批不在本批范围。

## 日常使用

新建的 Codex 工作线获得 `wait_for_user` 工具。当任务确实缺少事实或需要用户选择时，执行器通过该工具登记一个问题，结束当前轮次，再由 Namo 发送问题。等待时不会让模型持续运行或轮询。

用户可以引用这条问题直接回复，或按问题中提供的 `/resume WAIT-编号 你的回答` 命令恢复。编号绑定这一次等待，旧问题的回复不能唤醒后续另一轮等待。回复须来自原用户、原聊天及原话题，重复事件只处理一次。

`/task` 可查看当前问题与恢复命令；投递失败或结果不明不会重跑模型。`/cancel`、等待卡片的停止按钮和本地工作台可以取消，取消不会撤销已发生的操作。普通新消息不自动猜成等待答案，会在同聊天队列中等待；要继续原任务，请使用引用或恢复命令。

等待的只是事实信息或选择，不能代替发布、部署、删除、发送消息等操作的审批。模型层约束并不是命令级强制审批；现有任意联网命令的限制仍然适用，强制审批按 M3 后续单独建设。

## 运行与恢复

`task_waits` 记录所属任务、运行、thread / turn / tool call、问题、输入版本、等待状态及对应回复。生命周期如下：

1. 请求经身份与工具参数校验，先保存 `requested`，再回复工具调用。
2. 执行器立即中断该 turn；确认终止且没有并行或等待后的执行事件，才保存带等待标记的运行结果。
3. 接收服务将任务和入站消息置为 `waiting`、运行置为已结束的 `waiting`，开放等待事项并创建独立的 `wait:编号` 出站消息。此时不占用最终 `result`。
4. 用户回答经事务校验后置为 `answered`，保留原始入站正文，增加原任务输入版本并重新排队。新运行只发送问题、回答和本轮新增修订，恢复原 thread，不重复发送原始任务指令。
5. 多次等待分别保留记录，原始任务最终只生成一组 `result`。

等待释放全局并发名额和项目目录占位，但仍阻塞同聊天后续任务，防止同 session 并行。其他聊天可能在等待期间改动同目录，恢复指令要求重新核对当前状态；项目、权限指纹或 session 变化时拒绝执行，不自动新建上下文重跑。

请求落库后、确认 turn 结束前发生崩溃或协议违规，等待只能记为未确认，不能自动唤醒。独立运行已保存等待结果、接收服务尚未归档时，重连消费原结果，不再次调用模型。等待中的重启保留问题，回答已接受而未开工时只恢复排队的新一轮。

运行记录的安全终止以官方协议事件与所属进程组收口为依据，不代表任意命令启动的外部服务或外部操作已撤销。进程失联仍遵循已有本机核对与占位规则。

## 选择题按钮（schema 7，已上线）

真实验收发现，选择题卡片只有通用“查看详情 / 停止任务”按钮，容易与回答选项混淆。修复为 `wait_for_user` 增加可选 `choices`：2–4 个互不重复的简短答案，先与问题一同保存，再显示在问题下方；任务操作置于分隔线下。点击答案和文字回复使用同一个等待校验与恢复事务，保留原始任务、会话和已完成操作。按钮只携带随机令牌，答案取自保存记录，重复、过期、旧问题和非原用户点击不能再次恢复。开放问题及旧 schema 6 记录继续支持引用 / 命令回复。

新版 schema 7 只为 `task_waits` 增加可空 `choices` 列。旧线程的工具参数同样不会自动补装；需要选项按钮时先完成当前任务，再 `/new`。选择题仍不能用于外部操作审批。

2026-10-26，原 schema 6 真实私聊的问题卡已被用户看到，引用回复后后台确认原任务在同一 thread 的第二轮完成，最终回复取得平台回执。该轮未单独取得最终回复的用户确认；随后新版选择按钮与最终确认已获用户真实验收。

新版真实飞书验收：用户确认看到“中文 / 英文”答案按钮并在点击后收到最终回复。后台确认一个按钮回调被消费，保存的答案与被点击的持久选项一致，原任务在同一 thread 完成第二轮，仅发送一组最终结果，没有执行文件或命令操作。当前已验证引用恢复与选项按钮恢复；多轮等待、显式命令恢复、等待中重启与取消仍保留为完整真实场景的后续验收项。
